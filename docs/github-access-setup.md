# Настройка GitHub-доступа на другой машине

## Секреты и доступ

Этот файл намеренно не содержит паролей, personal access token (PAT), OAuth-токенов, cookies или содержимого локального хранилища учётных данных. Секреты привязаны к аккаунту и не переносятся в проект. Не запрашивай их у владельца в чате и не добавляй в Git, `.env`, командную строку или URL remote.

Публичное зеркало `mafckz/olx-kz-market-monitor` можно клонировать без входа. Основной репозиторий `grromankz-ctrl/olx-kz-market-monitor` приватный: для него владелец должен выдать доступ именно GitHub-аккаунту нового агента. Доступ к публичному зеркалу не даёт автоматически доступ к приватному.

В текущем рабочем окружении GitHub-доступ Codex и GitHub CLI были разными авторизациями: подключённая GitHub-интеграция читала и изменяла приватный репозиторий, а локальный `gh` был отдельно авторизован аккаунтом `mafckz` через системное хранилище учётных данных. Эта CLI-сессия не могла клонировать приватный `grromankz-ctrl` репозиторий, но могла отправлять изменения в публичное зеркало. Поэтому успешный вход в Codex не означает, что CLI уже авторизован так же, и наоборот.

## Подключение Codex

1. На новой машине войди в Codex под собственным аккаунтом.
2. В настройках подключённых приложений/интеграций Codex подключи GitHub и пройди официальный OAuth-поток под тем GitHub-аккаунтом, которому владелец выдал нужный доступ.
3. Для чтения приватного репозитория владелец должен добавить этот аккаунт в `grromankz-ctrl/olx-kz-market-monitor` либо в команду/организацию, имеющую доступ. Для отправки веток понадобится право записи; если его не выдали, работай в форке и открой pull request. Выдавай только необходимые права.
4. Проверь, что GitHub-интеграция видит репозиторий. Если приватный репозиторий не виден, попроси владельца проверить выданный доступ и подключённый GitHub-аккаунт; не пересылай чужой токен.

Названия и расположение пунктов настроек Codex могут отличаться между версиями приложения. Для работы только с публичным снимком GitHub-интеграция необязательна.

## Подключение GitHub CLI

Если агенту нужен `git`/`gh` в терминале, авторизуй его собственный GitHub-аккаунт локально через браузер:

```powershell
gh auth login --hostname github.com --git-protocol https --web
gh auth status
```

Заверши вход самостоятельно в открывшемся браузере. Не используй чужой пароль/PAT, `--with-token` или `--insecure-storage`. После входа обязательно проверь `gh auth status`: если системное credential store недоступно или завершилось ошибкой, GitHub CLI может автоматически сохранить токен в plaintext-файл. В таком случае не используй эту авторизацию для приватного репозитория: настрой поддерживаемое системное хранилище, повтори вход и проверь результат через `gh auth status`. Не копируй credential-файлы на другую машину.

Проверь доступ:

```powershell
gh repo view mafckz/olx-kz-market-monitor
gh repo view grromankz-ctrl/olx-kz-market-monitor
```

Первая команда проверяет публичное зеркало. Вторая сработает только после выдачи доступа к приватному репозиторию. Чтение и отправка изменений требуют разных уровней доступа: для push нужна запись; без неё используй fork и pull request. Если приватная команда сообщает, что репозиторий не найден или недоступен, сначала проверь `gh auth status` и попроси владельца выдать доступ нужному аккаунту. Не пытайся обходить проверку доступа.

GitHub CLI сохраняет токен в системном credential store, если он доступен; иначе возможен автоматический fallback в plaintext-файл. Проверяй фактическое место хранения через `gh auth status` и не полагайся только на отсутствие флага `--insecure-storage`. Если для автоматизации всё же требуется токен, создай отдельный минимально привилегированный токен под конкретный репозиторий, сохрани его только в поддерживаемом хранилище секретов и никогда не добавляй в файлы проекта. При утечке отзови токен в GitHub.

## Клонирование проекта

Для работы с публичным снимком:

```powershell
git clone https://github.com/mafckz/olx-kz-market-monitor.git
cd olx-kz-market-monitor
git switch main
git pull --ff-only origin main
```

Используй приватный remote только после того, как владелец подтвердил доступ твоему аккаунту. Не вставляй PAT в HTTPS URL remote.
